Committing key wrap: AES-256-GCM plus an HMAC-SHA256 key-commitment tag, with optional padding to a fixed total size.

§Threat model

The adversary holds any number of wrapped keys and controls every byte handed to unwrap_key. The guarantees are:

  • A wrong KEK always fails. AES-GCM alone is not key-committing (a ciphertext can be crafted to decrypt validly under two keys; Albertini et al., How to Abuse and Fix Authenticated Encryption with Key Commitment, USENIX Security 2022). Every wrapped key therefore carries HMAC-SHA256(kek, KEY_WRAP_COMMITMENT || version || nonce), the “UtC” shape of Bellare and Hoang, Efficient Schemes for Committing Authenticated Encryption (EUROCRYPT 2022): a PRF of the key over the public header, verified in constant time before the payload is accepted. HMAC-SHA256 with a 32-byte key is collision resistant in the key, so no two KEKs verify the same record.
  • Context is binding. The caller’s non-empty context (for example vault/v1/root/epoch-3/locator-xyz) is authenticated as AES-GCM associated data together with the version byte and the payload length, so a record wrapped for one purpose cannot be unwrapped for another.
  • Fixed size, random-looking output. For a given key length every output has the same length; wrap_key_padded pads under the AEAD so any record can be made exactly total_len bytes with the true key length hidden inside the ciphertext. Apart from the leading version byte, every output byte is a CSPRNG nonce, a PRF output or AES-GCM ciphertext, so records hide among other opaque files (output_bytes_look_random is a smoke test of this, not a proof).
  • Errors are opaque where the adversary can reach them. Commitment mismatch, tag failure, bad inner length and non-zero padding all surface as the same AeadError::DecryptionFailed string, and the AES-GCM decryption is always attempted so the two checks cannot be told apart by timing either. Structural checks on public bytes (version byte, impossible length) report AeadError::MalformedEncoding.

Out of scope: hiding the existence of a wrapped record of a given size (callers choose total_len to match their cover traffic) and protecting the KEK itself.

§Wire format (version 1)

WrappedKey = version (1, = 0x01)
          || nonce (12, CSPRNG)
          || commitment (32) = HMAC-SHA256(kek, KEY_WRAP_COMMITMENT || version || nonce)
          || AES-256-GCM(kek, nonce, aad, payload) || tag (16)
payload   = key_len (1) || key (16 | 32 | 64) || zero padding
aad       = version (1) || payload_len (u32 BE) || context

Total length is 62 + key_len + padding; wrap_key uses no padding and wrap_key_padded chooses the padding so the total equals total_len.

Constants§

COMMITMENT_LEN
Length of the HMAC-SHA256 key-commitment tag.
KEK_LEN
Length of the KEK in bytes (AES-256-GCM).
KEY_WRAP_OVERHEAD
Bytes every wrapped key carries in addition to the key itself and any padding: version || nonce || commitment || key_len || tag.
KEY_WRAP_VERSION
Version byte at offset 0 of every wrapped key produced by this module.
MAX_WRAPPED_LEN
Longest accepted encoding (1 MiB). Padded root records are meant to resemble ordinary files, not bulk data; the cap bounds the AES-GCM work an attacker can trigger through WrappedKey::from_bytes + unwrap_key.
MIN_WRAPPED_LEN
Shortest valid encoding: a 16-byte key with no padding.
SUPPORTED_KEY_LENS
Key lengths accepted by wrap_key.

Functions§

unwrap_key
Unwraps wrapped under kek and context, returning the original key with any padding removed.
wrap_key
Wraps key (16, 32 or 64 bytes) under kek, bound to the non-empty context. The output is KEY_WRAP_OVERHEAD + key.len() bytes.
wrap_key_padded
Like wrap_key, but pads the plaintext under the AEAD so the encoding is exactly total_len bytes. The real key length travels inside the ciphertext; unwrap_key strips the padding after authentication.
