RFC 9106: Argon2id memory-hard password-based key derivation

Argon2id derives a key from a password and a salt while forcing every guess to fill and revisit a configurable amount of memory. It is the variant RFC 9106 §4 recommends when the deployment does not know which Argon2 type to pick.

This module wraps the RustCrypto argon2 crate (raw-hash API only, no PHC string format) with:

  • Parameter validation against RFC 9106 §3.1 plus library floors (Argon2Params::validate)
  • A memory cap enforced through ResourceLimits::max_argon2_memory_kib before any allocation
  • Zeroized working memory and output (Argon2idResult)
  • Machine-local cost calibration (Argon2Params::calibrate)

§Threat model

  • Offline guessing. An attacker who obtains the salt, the parameters and anything derived from the key (a ciphertext, a verifier) can test password guesses offline. Argon2id does not stop this; it makes each guess cost memory_kib KiB of memory for the full duration of iterations passes. Low-entropy passwords remain guessable; the parameters set the price per guess.
  • Memory hardness. Fast hashes such as PBKDF2 parallelise cheaply on GPUs and ASICs because each guess needs almost no memory. Argon2id binds cost to memory bandwidth and capacity, where attacker hardware has far less advantage. RFC 9106 §7.2 bounds the best known time-memory trade-off against multi-pass Argon2id to a factor of about 1.33.
  • Salt length. The salt makes precomputed tables useless and forces the attacker to attack each password record separately. RFC 9106 §3.1 recommends 16 bytes; §4 step 7 allows 64 bits (8 bytes) where space is short. This module rejects salts shorter than 8 bytes and rejects all-zero salts, which indicate uninitialised buffers.
  • Side channels. Argon2d indexes memory by password-dependent values, which leaks through cache timing to a co-located attacker. Argon2i uses data-independent indexing but is weaker against trade-off attacks. Argon2id runs the first half of the first pass data-independently and the rest data-dependently, so a cache-timing observer learns less than with Argon2d while trade-off resistance stays close to Argon2d. It is not fully constant-time: an attacker who can observe memory access patterns during the data-dependent phase still learns something.
  • Denial of service. Argon2 parameters often come from stored or deserialized records. The memory cap, the iteration cap and the output length cap bound the work any single call can be made to do.

§Not exposed

RFC 9106 also defines an optional secret value K and associated data X. The public API exposes neither: Argon2id takes no domain-separation context in this library. The crate-internal path that feeds them is used only to replay the RFC 9106 §5.3 test vector. The underlying crate caps associated data at 32 bytes, while the RFC allows up to 2^32 - 1.

§FIPS 140-3

Argon2id is not a NIST-approved KDF. Like BLAKE2, it stays compiled under the fips feature so callers can reach it explicitly, but no policy-engine path selects it. Deployments that must stay in an approved mode should use pbkdf2.

§Lanes

This build does not enable the argon2 crate’s parallel feature, so lanes (parallelism) are computed one after another on a single thread. parallelism still changes the output, as RFC 9106 requires.
