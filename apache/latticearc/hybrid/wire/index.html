§Compact binary wire format (v1)

A fixed-layout, versioned binary encoding for the hybrid types that applications store or transmit: hybrid KEM public keys, hybrid KEM encapsulations, hybrid ciphertexts, hybrid signature public keys and hybrid signatures. Intended for fixed-size records on disk or untrusted storage where JSON and CBOR are unwanted. The normative specification, including the compatibility policy, is docs/WIRE_FORMAT.md.

§Layout

magic "LA" (2) | version = 1 (1) | type tag (1) | algorithm id (1) | body

Every body field has a length fixed by the algorithm id, so there are no length prefixes except for the variable AES-256-GCM ciphertext inside a HybridCiphertext (one u32 big-endian prefix, capped at MAX_SYMMETRIC_CIPHERTEXT_LEN). Trailing bytes are rejected, so each value has exactly one encoding.

TagTypeAlgorithm id
0x01HybridKemPublicKeyML-KEM level (1, 3, 5)
0x02EncapsulatedKeyML-KEM level (1, 3, 5)
0x03HybridCiphertextML-KEM level (1, 3, 5)
0x04HybridSigPublicKeyML-DSA parameter set (2, 3, 5)
0x05HybridSignatureML-DSA parameter set (2, 3, 5)
0x06reserved for WrappedKey—

Algorithm ids are the discriminants of MlKemSecurityLevel and MlDsaParameterSet (the NIST security category).

§Decoding guarantees

  • Total: every input yields Ok or a WireError; no panics.
  • The input length is checked against the type’s hard maximum (WireEncode::MAX_WIRE_LEN) before anything is parsed or allocated.
  • Allocation is bounded by the input actually supplied: a length prefix is only honoured when that many bytes are present.
  • Structural only: component bytes are not validated cryptographically (point/modulus checks happen at first use, as with HybridKemPublicKey::from_bytes).

§Error detail

WireError variants distinguish structural failures (truncation, version, type tag, trailing bytes). Every check reads only the public, attacker-supplied bytes and runs before any key material is touched, so the distinction reveals nothing the attacker did not already choose. Decryption and verification of a decoded value keep their opaque errors.

§Relationship to HybridKemPublicKey::to_bytes

HybridKemPublicKey::to_bytes predates this module and carries its own version byte, a 1/2/3 level tag and u32 length prefixes. It is left unchanged for existing stored keys. This format uses the shared header so all hybrid types share one envelope and one version rule, and drops the length prefixes because the algorithm id fixes every length.

§Example

use latticearc::hybrid::kem_hybrid::generate_keypair;
use latticearc::{HybridKemPublicKey, WireEncode};

let (pk, _sk) = generate_keypair()?;
let record = pk.to_wire()?;
assert_eq!(record.len(), 5 + 1184 + 32);
let restored = HybridKemPublicKey::from_wire(&record)?;
assert_eq!(restored.ml_kem_pk(), pk.ml_kem_pk());
